# Screenshot chat with LFM2.5 VL 3B and 450M

All Chat page code is grouped in this package. Matching JVM tests and the optional phone test are in the `chat` folders under `src/test` and `src/androidTest`. MainActivity supplies navigation and activation through the existing model selector; GgufLlmManager supplies shared, serialized GGUF inference.

## Current workflow

The only initial case-specific input is the user's original question. Chat requires both LFM2.5 VL presets with their matching projectors. **3B generates prompts and the final explanation; 450M verifies and extracts images.** **Set up chat models** activates 3B when both models are downloaded, or opens **Models** to finish downloading them. GGUF test remains available for other models.

1. A 3B text call rewrites the original request without its time restriction. A second 3B text call receives that model-written rewrite unchanged and generates both image questions and their empty extraction response format. Fixed, topic-independent system wrappers define each protocol. The app retains the original question for date filtering and retrieval. Rewrites that drop the subject or alter non-temporal quantities are rejected. The verification question must be a yes/no question. Planning errors receive bounded generic corrections (up to two rewrite attempts and three plan attempts, stopping if an error repeats) before images are read. Both image questions must omit time restrictions; the app applies the original date window.
2. Retrieve saved descriptions/tags/notes and current embeddings before decoding images. The original question supplies retrieval terms and dates; LFM's verification question supplies additional semantic context. GGUF memory is released throughout retrieval.
3. Hold an exclusive vision batch for all candidates. The first uncached call loads 450M and its projector; subsequent checks reuse that allocation. No 3B writing call occurs between images, and gallery/idle/background operations cannot switch models during the batch.
4. First LFM visual call per candidate: use the unchanged model-written verification question and return decision/evidence JSON. NO skips extraction; YES and MAYBE receive a second LFM call using the prepared model-written extraction question and response format, with the first-pass model evidence and a quoted on-device text-reading aid from that same image. Both are untrusted observations for the second call to check. The text reader joins geometrically aligned labels and values before moving down the image. If an explicit payment/date label is unreadable, it re-reads that one candidate at its original resolution (up to 4096 pixels), retaining both observations so conflicting readable values stay a conflict. The extra bitmap is released before vision resumes; 450M keeps its existing 1536-pixel image size. The generic extraction wrapper defines value, unit, event_date, record_id and evidence; the question defines the case-specific fact. MAYBE remains uncertain.
5. Release 450M at batch completion, failure or cancellation. For spending, a unique explicitly labeled completed/payment date from the image's text can resolve small digits misread by vision. For an unqualified spending total with an empty or zero extraction value, a positive amount can be recovered only when the YES verifier quoted one unique amount/currency and it agrees exactly with an explicitly labeled paid amount read from that same image. A model-read numeric value can use the printed paid label's currency only when their amounts agree exactly. These aids do not apply to item-specific spending, uncertain checks or conflicting values/currencies. Preserve raw model JSON and show printed evidence separately. Apply the original date range, exact decimal arithmetic, currency grouping and duplicate checks to confirmed facts.
6. If accepted evidence remains, load 3B once more for a short explanation, using compact accepted amount/date rows for spending questions. Display a spending explanation only if it reproduces every app-calculated currency total; otherwise retain the app's result and coverage. Release 3B when the request ends.

A normal request makes one rewrite call, one planning call and one final-answer call, plus at most two LFM visual calls per candidate. The bundled text reader runs only for verified/uncertain candidates reaching extraction, not the whole library. A fully cached batch does not allocate a GGUF vision model. Case-specific questions still come from 3B and pass forward unchanged. The final answer lists every counted amount; its arithmetic does not depend on the bounded examples sent to the final text model.

The general wrappers require flat image JSON, string evidence and preservation of raw visible dates and units. The plan must contain two concrete questions and the five null response slots. Invented planning numbers, answers instead of questions, missing format keys and malformed JSON are rejected. Validation retries use only a general error, never a subject-specific correction or expected image facts. The plan's full JSON schema is retained in its trace and cache identity but is not duplicated in native input. The native grammar sampler remains disabled because it aborts on LFM tokens. These checks validate the protocol, not general semantic correctness.

## Files

- **ChatScreen / ChatWorkflowDetails:** conversation, model activation, progress, sources, stop/new chat, expandable and selectable prompts/raw responses, cache indicators and errors.
- **RagChatViewModel:** request lifecycle, cancellation and UI state. Saved-image Chat checks both model downloads and requires 3B as the selected planning model. It cannot silently fall back to the old receipt prompt.
- **ChatWorkflowSchemas:** topic-independent JSON output contracts for text writers; these are prompt contracts, not native grammar decoding.
- **ChatWorkflowModels:** stage routing: VERIFY/EXTRACT use 450M, all text stages use 3B. Each trace names the model that handled that stage.
- **ChatWorkflowPrompts:** fixed general instructions, input assembly and wrapper fingerprint.
- **ChatWorkflow:** model-driven handoffs, YES/NO/MAYBE branching, a complete upfront plan and shape validation. It is independent of Android inference and image decoding.
- **ChatWorkflowRunner:** repository/inference/cache integration, streamed traces, bitmap lifetime, date/record selection, totals and final answer.
- **ChatAnswerValidation:** suppresses spending explanations that omit or change a required currency total. It also hides explanations containing internal prompt labels. Matching totals does not establish correctness of every sentence.
- **ChatWorkflowFacts:** adapter for common LFM-selected amount/date/currency fields, conservative date parsing and exact totals. This adapter never changes the generated prompts or schema.
- **ChatDateWindows / ChatQuery:** calendar periods, numeric-date convention, temporal term removal and explicit event/capture/import date basis.
- **ChatImageDateReader / ChatImageDates / ChatEventDates:** distinct capture/import/file dates, EXIF headers and event-first date provenance.
- **ChatImageTextReader / ChatPrintedEventDate:** bundled Latin text recognition and strict identification of explicitly labeled event dates. These dates cannot supply payment relevance or amounts. Missing/conflicting labels, unresolved date order and due dates do not override the model's date.
- **ChatWorkflowCache:** dedicated `chat_workflow.db`, scoped to exact stage/input, wrapper version, model/projector files and image byte SHA-256/current context. Planning, verification and extraction may be reused. Final answers are generated afresh. Unreadable images fail before cache lookup; the schema is also part of the cache identity. Storage is bounded to 3,000 responses.
- **ChatQuery / ChatRepository / ChatCandidateSelector:** original date range, stored-context retrieval, current-vector checks and cheap candidate screening. ChatScreen previews the resolved range before sending a question.
- **ChatModelTest:** raw GGUF compatibility probes. Both LFM presets can run text and image probes; other vision models still require an image.
- **ChatPrompts / ReceiptFacts / ChatReceiptCache:** previous receipt-specific implementation retained for reference and existing tests; saved-image Chat no longer calls it.

## GGUF runtime

Model selection now validates the downloaded files and records the choice without allocating a native model. GgufLlmManager loads the necessary bridge on its first request. Its residency controller releases the previous model/context and projector synchronously before loading a different model or bridge. **3B text and 450M vision never remain resident together.** Consecutive requests on the same bridge/model can reuse the allocation.

Chat releases GGUF allocations throughout retrieval and after completion, failure or stop. It also recycles a retained candidate bitmap before text-only calls. General GGUF analysis unloads after 15 seconds idle and on memory-pressure/background callbacks, then reloads on demand. The selected model and downloaded files survive this release. Gallery can restore the selected image model through the same on-demand path. Inference, loading, unloading and deletion share the inference mutex; native completion is awaited even when the calling coroutine is cancelled.

The bundled Llamatik 1.1.1 native grammar decoder aborts on an LFM token with `Unexpected empty grammar stack after accepting piece`. Chat describes the JSON contract in normal instructions and validates the result instead. The complete planning schema is retained in the trace/cache identity without duplicating it in native input. Kotlin exception handling cannot recover a native SIGABRT, so this path is not invoked.

This policy covers the GGUF bridges. The embedding library in this version has no public native release API; freeing a Java reference is not proof of freeing its native model. The connected 8GB test phone has no EmbeddingGemma files. The optional memory test checks real process mappings for the GGUF files and records RSS/native-heap measurements; this does not prove arbitrary model combinations fit all available-memory conditions.

Text planning uses LiquidAI's recommended temperature 0.2, top-k 50 and repeat penalty 1.0. The upstream visual bridge retains its existing built-in sampling settings.

## Dates, retrieval and numeric limits

Date-language detection is rule-based app code in ChatDateWindows/ChatQuery, including the initial spending keyword category. Actual ranges are computed from the phone's date and the requested year. LFM does not generate calendar boundaries. It removes the time restriction and generates the case-specific image questions. Supported short fragments do not require a full sentence: fresh checks recognized `Oct 1 spending` and `spending last week`. The first passed with MYR 5.72; the weekly fragment selected/counted all five correct images but its amount check failed after 450M read 7.77 as 1237. See the short-query evidence in [calendar period validation](../../../../../../../../artifacts/chat-date-periods/README.md). Arbitrary date wording remains limited by the parser's supported patterns.

- Last/past/previous week (including "past last week") includes today and the date seven days ago, as requested for September 30–October 7. This inclusive range has eight calendar dates; explicit last/past 7 days remains seven dates including today. "This week" and explicit "last/previous calendar week" use Monday–Sunday boundaries. Relative dates resolve once from the phone's date at request start. Submit a new question to use a changed date.
- Calendar periods also support last month (the full previous month), this month (through today), named months with optional years, written/ISO/numeric days, and inclusive written/ISO/numeric ranges. Missing years use the phone's current year. A range with one explicit year shares it across both dates and handles a December–January crossing. Month weeks mean 1–7, 8–14, 15–21, 22–28, and 29–month end, per the user's choice. A nonexistent fifth week is rejected. "Week of DATE" starts seven days at that date. Unsupported, invalid, reversed or conflicting periods ask for a clearer date rather than searching all dates. Temporal phrases are removed from retrieval subject terms.
- Relevance screening runs on saved text and embeddings, not a visual scan of the whole library. Spending has no arbitrary top-k cap; general questions currently use up to 10 candidates. A library with many genuinely relevant candidates can still need many image calls on its first question.
- Capture and import dates are separate facts. A visible event date takes priority for normal questions; a real capture date is used only when no event date is available. MediaStore DATE_TAKEN uses milliseconds; DATE_ADDED and DATE_MODIFIED use seconds. A photo's EXIF DateTimeOriginal supplies capture when MediaStore lacks one, with its offset when supplied. Import or file-modification time never substitutes for capture. Explicit "images taken/captured" and "images imported/added" questions use that metadata basis instead. The preview and counted records show the basis used.
- Stored matching numeric, written or ISO event dates can admit old records captured/imported later. Final model extraction and labeled text are checked again against the period, so saved descriptions cannot establish a counted event by themselves. An unreadable or ambiguous event date is not replaced with capture metadata. Images can still be missed when stored context and capture metadata both point outside the period; missing capture metadata leaves relevant event-date candidates for visual inspection. The UI shows library/relevance/date-filtered counts.
- ISO and textual dates are recognized. The visible **Receipt dates** selector chooses day/month/year (default), month/day/year, or leaves ambiguous dates unresolved. The same convention applies to numeric dates in the user's question. Under day-first, 01-10-2026 means October 1. An invalid selected convention is rejected rather than reversed. A unique printed Completed Time, Payment Date, Transaction Date, Paid On or similar explicit label can establish the spending date even when vision misreads the year. Conflicting labels or an unlabeled/due date cannot supply this reading aid.
- The numeric adapter accepts common model-selected fields such as `amount`, `amount_paid`, `total_amount`, `total_spent`, `total_expenditure`, `currency`/`unit` and `transaction_date`/`event_date`; it does not mandate those fields to LFM. A value like `RM5.72` supplies its own unit. A unit in LFM's quoted verification evidence can also be used when it is directly attached to the exact extracted amount; unrelated values cannot supply the unit. An unrecognized optional unit cannot erase an exact embedded/quoted currency; valid conflicting currencies still exclude a record. Empty-value recovery requires agreement between LFM's unique first-pass quote and an explicit paid label, as described above. Unknown names, conflicting amounts/units, missing/ambiguous currency and unreadable required dates are excluded from totals while raw JSON and source-specific exclusion reasons remain visible. RM normalizes to MYR; ambiguous `$` does not become an inferred currency. Dates never come from a currency quote.
- YES means model-judged relevance, not independently established payment completion. Explicit unpaid/pending/refund/incoming status is excluded when present; a generated schema can omit necessary status or value-selection rules. Review raw evidence and sources. General correctness across invoices, refunds, item amounts and arbitrary schemas remains a model/evaluation limitation.
- MAYBE is extracted for inspection but never counted as confirmed. Duplicate image byte SHA-256 hashes and explicit transaction references can remove repeats; equal merchant/date/amount alone cannot collapse distinct purchases.
- Sessions remain in memory while the destination is retained. New chat clears displayed turns, not the persistent cache. Sources and raw prompts/results can be inspected for each stage.

## Validation

The count/date correction uses the bundled [ML Kit Latin text reader](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) (`com.google.mlkit:text-recognition:16.0.1`). Its model is packaged in the APK rather than downloaded at request time. The optional `ChatPrintedDatesDeviceTest` verifies independently inspected printed dates in explicitly supplied saved fixtures. `LfmSavedImagesDeviceTest` can freeze the reference date through `chatToday` to reproduce a reported range across midnight; it can assert the complete accepted source set and total after inference. Expected dates, amounts and source IDs are test assertions, never prompt inputs. Current evidence is in [chat-complete-week](../../../../../../../../artifacts/chat-complete-week/README.md).

The broader date implementation passes 114 JVM tests and three installed-phone calendar/metadata/EXIF/date checks. Five fresh production runs on the 8GB OnePlus 7T passed: October 1 (MYR 5.72), last month and September 2026 (MYR 18.58 each), September's fifth week (MYR 13.00), and September 30–October 2 (MYR 21.05), using October 8, 2026 as the reference date. Every counted date/amount matched its screenshot; every candidate had two visual calls, with no exclusions or failed checks. The same fixed rewrite/planning wrappers handled all five requests. Month-week and range planning each needed one generic placeholder correction. Uncached full native tests took 144.215–265.875 seconds including loading and final writing. Current raw model responses, independent comparisons and the installed debug APK hash are recorded in [calendar period validation](../../../../../../../../artifacts/chat-date-periods/README.md). The user question remains the only initial case-specific model input; expected source sets, amounts and dates are assertions after inference.

The previous count/date correction passed 88 JVM tests, the actual-phone date parser and all six printed date/paid-label checks. A fresh production run on the 8GB OnePlus 7T counted six independently inspected September 30–October 7 payments exactly once, totaling MYR 42.94 with no exclusions, duplicates or failed image checks. Each accepted amount/date matched its screenshot. Two 3B planning calls (one retry), 12 450M visual calls and one 3B explanation took 343.278 seconds. That validates those fixtures, without promising latency or accuracy for arbitrary libraries. Evidence and retained failed attempts remain in the previous checkpoint above.
